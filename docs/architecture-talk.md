# 架构讲解稿（面试 / 客户汇报用）

> 建议讲解时间：10–15 分钟。可结合一次测试报告和 Trace 回放演示。

## 1. 项目目标与分层

这套框架运行在 Automation Exercise 公开演示站，目标是让关键业务流程可重复验证、
失败可诊断，并且便于持续扩展。

```text
tests/        场景编排与断言
fixtures/     用户注册、登录态和共用浏览器设置
pages/        页面定位器与业务动作（POM）
testdata/     用户、商品、表单和支付数据
config/       环境变量及超时配置
utils/        日志、数据生成、网络拦截和无障碍扫描
```

页面变化优先修改对应页面对象；测试描述业务过程，不重复堆叠页面定位器。新数据放在
`testdata/`，动态邮箱由数据生成工具提供。

## 2. 关键工程决策

### 页面对象与定位

定位优先级为 `[data-qa]`、`#id`、语义 class、文本。页面定位器和可复用操作放在
`pages/`，例如注册、支付和结算动作；`tests/` 负责调用并断言结果。

### 同步与失败证据

使用 Playwright 自动等待、URL 等待和 web-first assertions，不用固定 sleep。
截图、视频和 Trace 按配置仅在失败时保留；HTML/JSON 报告和产物写入独立时间戳目录。
排查时先看失败步骤和截图，再在 Trace 中核对 DOM 快照、动作时间线与网络请求。

### Fixtures 与数据

`registeredUser` 会创建唯一邮箱的测试用户；`authedUser` 依赖注册 fixture 并提供登录态。
这减少了每个用例重复编写注册/登录装配的代码。用户、商品、地址、支付卡及异常输入
分别放在 `testdata/`，便于数据驱动扩展。

### 网络拦截与 Mock

广告/统计请求由 fixture 拦截以减少不稳定因素。加购流程通过网络监听核对请求，
并通过模拟 500 响应覆盖失败路径，证明前端异常行为可被独立验证。

### 无障碍扫描

独立 axe-core 扫描结果写入 `reports/accessibility/`，记录违规规则和受影响节点；
发现违规会使对应无障碍测试失败。无障碍门禁只在专用扫描套件中执行，不重复阻断
普通功能回归。

## 3. 浏览器执行策略

当前仅启用 Desktop Chrome 作为回归门禁。Desktop Edge、Firefox、WebKit、Pixel 7
（移动 Chromium）和 iPhone 13（移动 WebKit）项目已在 `playwright.config.ts` 中准备，
但暂时以注释停用；启用后需安装/确认对应浏览器，并单独验证兼容性。

视觉像素比较仅在 `chrome` 项目执行，避免不同引擎的字体与抗锯齿差异产生噪声。
基线覆盖首页、商品目录和详情、登录、联系表单、购物车、结算、支付及订单确认；
动态账户信息会遮罩。

## 4. 用例组织与覆盖

测试按认证、商品/购物车、结算、联系表单和视觉回归等职责拆分。官方测试计划列出
26 个场景，其中 TC7 按要求永久跳过，其余场景与自动化文件的映射见
[`automation-test-plan.md`](./automation-test-plan.md)。相关场景共享 setup，避免无意义的
匿名/登录态重复测试；注册用户结算和结算时注册保留为不同路径，因为身份建立时机不同。

## 5. 调试演示建议

1. 从 HTML 报告打开一次失败记录，查看失败步骤和截图。
2. 打开 Trace，回放失败前后的 DOM、动作和网络请求。
3. 需要交互式复现时使用 `npm run test:debug`；录制探索可使用 `npm run codegen`。

AI 可用于样板代码和文档草稿，但 locator、等待策略和站点行为需结合页面实际情况核实。
使用记录见 [`ai-usage-log.md`](./ai-usage-log.md)。
